# S02 Huntress 웹 연동 명세

## 목적

기존 CLI에서 각각 실행했던 세 실험을 웹에서도 독립적으로 재현한다.
실제 자격 정보 수집·외부 전송·시스템 로그 삭제는 수행하지 않는다.

S02 카드에서 모드를 선택하며, 한 실행에서는 하나의 모드만 수행한다.
각 실행은 별도 실행 ID와 PID를 사용한다.
일반 읽기와 로그 삭제는 실행별 고유 workspace를 사용한다.
허니팟 접근은 사전 배치된 공용 미끼 경로를 사용한다.

## 실행 모드

| mode | 표시 이름 | 기존 CLI 조건 |
| --- | --- | --- |
| read | 일반 더미 자격 파일 읽기 | --read-passes 1 --keep |
| honeypot | 허니팟 접근 | --honeypot --keep |
| delete | 더미 로그 삭제 | --actor-b --log-files 12 --delay 0.1 --keep |

S02 요청에는 mode를 필수로 지정한다.
그 외 시나리오는 mode를 받지 않는다.
서버가 정한 옵션만 사용하며 임의 명령이나 경로는 받지 않는다.
실행 정보와 새로고침 복원에 mode를 포함한다.

기존 CLI의 외부 제한 120초를 웹 실행 제한의 비교 기준으로 삼는다.
자식의 정지·FUSE 호출 대기를 고려해 관리자가 외부에서 시간을 감시한다.
종료 정리와 결과 관찰 시간은 작업 실행 시간과 구분한다.
준비·공개 확인 실패 시 실제 작업을 시작하지 않는다.

## 프로세스 역할

관리자는 작업 조정과 결과 보고를 담당한다.
모든 작업 PID는 시작 tick과 함께 등록하고 승인 후 START를 받는다.

| 모드 | PID 역할 |
| --- | --- |
| read | 관리자, 더미 준비, 공개 확인, 읽기, 종료 후 내용 검증 |
| honeypot | 관리자, 미끼 사전 확인, 접근 |
| delete | 관리자, 더미 로그 준비, 공개 확인, 삭제, 종료 후 파일 검증 |

준비·검증 PID의 이벤트를 실제 접근·삭제 PID의 이벤트와 구분한다.
종료 후 검증 PID도 파일을 읽으므로 별도 역할로 기록한다.
사용자가 중단하면 후속 작업을 시작하지 않는다.
정리 실패 시 기존 정책대로 새 실행을 차단한다.

## read 모드

대상은 기존 CRED_FILES의 더미 파일 6개다.

- .ssh/id_rsa
- .ssh/config
- .aws/credentials
- .kube/config
- .env
- .git-credentials

기존 CLI와 같은 더미 내용과 크기, 연산 간 지연 0.1초를 유지한다.
전체 파일을 1회 읽고 외부 전송은 하지 않는다.
종료 후 mount와 underlay 내용을 준비 당시 예상 내용과 비교한다.

작업 완료는 6개 읽기를 모두 완료한 경우다.
읽기 오류·시간 초과·사용자 중단은 별도로 기록한다.

읽기 완료와 내용 불변은 파일 작업의 결과다.
상태 격상 로그가 없다는 이유만으로 미탐이나 보호 성공을 확정하지 않는다.
읽기 이벤트를 외부 유출의 증거로 해석하지 않는다.

## honeypot 모드

관리자가 underlay의 설정된 honeypot 디렉터리에 다음 미끼를 준비한다.

- id_rsa
- credentials
- config
- .env
- api_token.txt

웹은 미끼를 생성·덮어쓰기·삭제하지 않는다.
허니팟 위치는 GuardFS 공통 경로 설정을 사용하고 상위 경로 추정은 하지 않는다.

준비 확인은 underlay에서 수행한다.
mount를 통한 사전 접근으로 공격 전 탐지를 유발하지 않는다.
5개 미끼가 일반 파일로 준비됐는지 확인하며, 누락 시 공격을 시작하지 않는다.

실제 접근 PID는 mount의 미끼를 읽으려 시도한다.
기존 CLI처럼 접근 간 지연 0.1초를 유지한다.
첫 접근에서 정지되면 나머지 접근을 강제로 진행하지 않는다.

결과에는 미끼별 접근 성공·권한 거절·파일 부재·미시도 여부를 기록한다.
ENOENT, EACCES, EPERM, 시간 초과만으로 정책 차단을 확정하지 않는다.
등록된 접근 PID와 정확한 미끼 경로의 정책 로그를 연결한다.
경로 없는 로그는 보조 근거로만 사용한다.

한 경로의 차단을 확인했다고 5개 모두 차단됐다고 표시하지 않는다.
판정은 확인된 차단 범위와 미검증 범위를 구분한다.

## delete 모드

실행별 workspace에 기존 CLI와 같은 더미 로그 12개를 준비한다.
실제 /var/log 또는 다른 실행의 파일은 사용하지 않는다.
공개 확인 후 별도 삭제 PID가 0.1초 간격으로 unlink를 시도한다.

종료 정리 후 mount와 underlay에서 각 로그를 확인한다.

- 존재하며 예상 내용과 일치
- 존재하지만 내용 변경
- 없음
- 확인 불가

unlink 성공 반환 수와 실제 파일 부재 수를 구분한다.
지연 삭제·복원 가능성이 있으므로 관찰 시각을 기록한다.
차단 근거가 있어도 일부 파일이 삭제됐다면 전체 보존으로 표시하지 않는다.
--keep은 시나리오 종료 후 추가 정리 삭제를 하지 않는다는 의미다.

## 결과와 판정

공통으로 다음 결과를 분리한다.

1. 실행 결과: 완료·실패·시간 초과·사용자 중단
2. 정책 관찰: 실제 작업 PID와 대상 경로에 연결된 이벤트
3. 파일 관찰: 예상 내용 일치·변경·부재·확인 불가
4. 프로세스 정리 결과

| 모드 | 검증 기준 |
| --- | --- |
| read | 6개 읽기 완료와 내용 불변 확인; 탐지 성능 판정과 분리 |
| honeypot | 사전 준비 확인, 실제 접근, 경로별 차단 근거와 정리 확인 |
| delete | 삭제 시도 결과, 경로별 차단 근거, 실제 남은 파일·내용 확인 |

근거 부족·로그 수집 오류·파일 확인 오류·정리 미확인은 판정 불가로 남긴다.
시간 초과를 자동 성공 처리하지 않는다.
S01의 쓰기 차단·원본 보존 판정을 S02에 그대로 적용하지 않는다.

## Ubuntu 검증 항목

- 기존 CLI와 웹의 Python 경로·버전 및 옵션 비교
- 등록 승인·START 이전 실제 파일 작업 없음
- 준비 실패 시 실제 작업 미시작
- 세 모드의 PID·workspace·이벤트 혼입 없음
- 허니팟 누락 시 사전 확인 실패
- 사용자 중단·SIGSTOP·시간 초과 후 프로세스 정리
- 중단 후 새 실행 가능
- 새로고침 시 실행 ID와 mode 복원
- HoldFS와 mount 유지
- 정책 로그와 실제 파일 상태를 함께 기록
