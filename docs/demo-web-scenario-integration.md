# HoldFS 웹 시나리오 연동 계획

2026-11-08 사용자와 확정한 시연 구성이다. 이 문서는 구현 계획이며 웹 연동 완료 기록이 아니다.

## 시나리오 구성

| 웹 ID | 시나리오 | 기존 시뮬레이터 |
| --- | --- | --- |
| S01 | IceFire 랜섬웨어 | `experiments/simulators/sim_scn_icefire.py` |
| S02 | DarkRadiation 랜섬웨어 | `experiments/simulators/sim_scn_darkradiation.py` |
| S03 | Huntress | `experiments/simulators/sim_scn_huntress.py` |
| S04 | Akira | `experiments/simulators/sim_scn_akira.py` |

기존 S01 정상 작업은 웹 시연 목록에서 제외한다. 기존 코드는 회귀 검증을 위해 보존한다.
기존 catalog의 S01~S05와 새 구성이 다르므로 이름만 바꾸거나 기존 실행 ID를 다른 시나리오로 해석하지 않는다.

## 파일 배치와 이름

기존 웹 실행 파일 `scenarios/s01_normal.py`와 같은 방식으로 저장소 루트의 `scenarios/`에 웹 실행용 모듈을 추가한다.

```text
scenarios/
├── s01_icefire.py
├── s02_darkradiation.py
├── s03_huntress.py
└── s04_akira.py
```

각 모듈은 해당 시나리오 연동 커밋에서 실제 실행 가능한 형태로 추가한다. 빈 파일이나 실행 불가능한 항목을 먼저 활성화하지 않는다.
웹 ID S01~S04와 파일 접두사 s01~s04를 일치시킨다.
`experiments/simulators/sim_scn_*.py`와 `scenario_lib.py`는 기존 CLI·테스트에서 참조하므로 원래 위치에 보존하고,
웹 모듈에서 필요한 작업 함수를 재사용한다. 시뮬레이터 전체를 복사해 두 구현을 따로 관리하지 않는다.
웹 모듈은 PID 등록·START 대기·진행 및 결과 보고를 담당하며, 원본의 준비/작업 분리와 자식 실행 흐름을 먼저 검토한다.
기존 `s01_normal.py`는 정상 작업 회귀 검증용으로 남기고 새 S01 catalog에는 연결하지 않는다.

## 공통 실행 계약

- runner는 서버에서 정한 시나리오와 옵션만 허용한다.
- 실행별 고유 workspace를 시뮬레이터 target에 전달한다. 기존 CLI의 고정 폴더를 웹 실행에 재사용하지 않는다.
- 실제 파일 작업 프로세스는 PID와 시작 tick을 등록하고 등록 확인 및 START 신호 이후 작업한다.
- 준비 프로세스와 공격 모의 작업 프로세스를 구분한다. 자식 도구가 파일 작업을 수행하면 그 PID도 실행에 연결한다.
- 기존 실행 그룹 중단·정리 확인·정리 실패 시 새 실행 차단 동작을 유지한다.
- 파일 작업 결과, 프로세스 종료 결과, 이벤트 수집 결과, 탐지·보호 판정을 구분한다.
- 프로세스 종료 코드 0 또는 MEDIUM 진입만으로 보호 성공을 판정하지 않는다. 차단으로 인한 작업 실패도 보호 실패로 단정하지 않는다.
- 중단은 테스트 프로세스 종료를 뜻한다. HoldFS의 지연 작업 폐기나 원상복구를 보장하지 않는다.
- HoldFS 탐지 정책·ML 임계값·학습 모델은 웹 연동을 위해 변경하지 않는다.

## 시나리오별 연동 검토

| 시나리오 | 연결할 작업 | 구현 전 확인할 사항 |
| --- | --- | --- |
| IceFire | 더미 문서 준비, 덮어쓰기, 확장자 변경, 모의 노트 | 준비/작업 PID 경계, 차단 시 종료 및 결과 보고 |
| DarkRadiation | openssl을 통한 더미 파일 변환 | openssl 자식의 작업 전 등록 방법, 신뢰 분류 관찰; openssl 부재 시 다른 엔진으로 자동 대체하지 않음 |
| Huntress | Actor C 읽기, 허니팟 접근, Actor B 로그 삭제 | 아래 제안대로 한 실행에서 별도 PID로 순차 수행; 허니팟 경로와 PID 연결 범위 보완 |
| Akira | 더미 VM 파일의 부분 덮어쓰기 | 비율·위치·크기 옵션과 결과 관찰 방법 확정 |

아래 값은 코드 검토에 따른 웹 1차 구현 제안이다. VM에서 탐지 효과가 검증된 설정으로 해석하지 않는다.
사용자 지정 옵션 UI는 먼저 만들지 않고 서버의 명시적인 실행 설정으로 시작한다.
정책 자동 판정은 별도 기준이 정해질 때까지 `not_checked`를 유지한다.

## 1차 실행 옵션 제안

### IceFire CLI 비교 기준 변경

사용자가 이전에 보존을 확인한 CLI 조건과 비교하기 위해 S01 웹 설정을 문서 10개·각 64KiB로 변경했다.
작업 자식은 백엔드 Python 대신 프로젝트 루트 `venv/bin/python3`를 명시적으로 사용하며, 없으면 사전 확인에서 실패한다.
준비 제한과 공격 제한은 별도 인자로 관리하고 기본값은 각각 30초다. 실행 JSON의 `execution_settings`에 설정을 기록한다.
예정 연산 수는 준비/확인 각각 11회, 공격 32회로 계산한다. 아래 표의 S01 12개 설정보다 이 변경 기록을 우선한다.
PID 구성과 외부 종료 방식까지 CLI와 같아진 것은 아니다. HIGH 정지 시 시간 초과는 여전히 발생할 수 있으며,
이 변경이 mount/underlay 내용 불일치를 해결했다는 의미는 아니다. 새 workspace에서 실제 내용 비교가 필요하다.

| 항목 | S01 IceFire | S02 DarkRadiation | S03 Huntress | S04 Akira |
| --- | --- | --- | --- | --- |
| 파일 | 12개, 각 64KiB | 10개, 각 64KiB | Actor C 6개, Actor B 12개, 각 256B | 8개, 각 64KiB |
| 방식 | docx/pdf/xlsx 순환, 전체 난수 덮어쓰기 | `/usr/bin/openssl` AES-256-CBC, 파일별 자식 | 일반 읽기 → 허니팟 접근 → 로그 삭제 | VM 확장자 순환, 앞부분 20% 난수 덮어쓰기 |
| 쓰기 청크 | 16KiB | openssl 자체 처리 | 해당 없음 | 16KiB |
| 연산 간 대기 | 파일별 0.15초 | 파일별 0.15초 | 읽기 0.1초, 허니팟 0.1초, 삭제 0초 | 파일별 0.15초 |
| 작업 제한 | 작업 단계 30초 | 작업 단계 30초, 자식 대기도 남은 시간 이내 | 하위 작업별 10초 | 작업 단계 30초 |
| 준비 제한 | 생성 30초, 공개 확인 30초 | 생성 30초, 공개 확인 30초 | C/B 각각 생성 15초, 공개 확인 15초 | 생성 30초, 공개 확인 30초 |
| 보존 | 실행 산출물 보존 | 실행 산출물 보존 | 남은 파일 보존 | 실행 산출물 보존 |

- 공통 runner 전체 제한은 기존 150초를 유지한다. 준비·등록·작업 시간을 포함하며 경과 시간은 monotonic 시계로 계산한다.
- 시간 제한은 파일 루프 조건만으로 보장하지 않는다. SIGSTOP·자식 wait·멈춘 FUSE 호출은 runner의 외부 제한과 그룹 정리로 처리한다.
- 보존은 추가 정리 삭제를 하지 않는다는 의미다. 시나리오 본래의 표식 삭제·더미 로그 삭제는 그대로 시도한다.
- 웹 경로는 runner가 발급한 workspace만 사용하고 실제 중첩 workdir도 결과에 기록한다. underlay는 관찰·검증에만 사용한다.
- S01은 모의 노트 생성과 표식 `demo` 삭제까지 작업 수에 포함한다. 원본에서 표식 생성은 관리자 PID가 수행하므로 웹에서는 준비 역할로 옮겨 공격 프로필을 분리한다.
- S02는 openssl 부재를 PRECHECK 실패로 보고한다. inprocess/shred로 자동 대체하지 않는다. 현재 원본에는 shred 엔진도 있으나 별도 비교 실험으로 남긴다.
- S03은 세 하위 작업을 별도 PID로 순차 실행하는 구성을 제안한다. 앞 작업이 파일 오류로 끝나도 그룹 정리가 확인되면 다음 작업을 관찰할 수 있다. 사용자 중단·전체 제한·정리 실패 시 후속 작업은 시작하지 않는다.
- S03의 삭제 대기 0초는 기존 CLI 기본 0.1초와 다르다. 12개 삭제를 짧은 구간에 시도하기 위한 웹 실험값이며 격상을 보장하지 않는다.
- S04의 tail 비교는 후속 옵션으로 남긴다. head 20%는 헤더 보존 실험이 아니며 UI에서도 그렇게 설명한다. 준비 파일 용량을 임의로 늘리지 않는다.

## PID와 실행 제어 설계

관리자는 진행·결과 보고와 자식 등록만 담당한다. 준비/공개 확인/실제 작업을 별도 역할로 등록한다.
작업 역할은 시나리오 이름을 포함해 구분한다(예: `icefire_prepare`, `icefire_verify`, `icefire_attack`).

| 시나리오 | 실제 작업 PID 구성 |
| --- | --- |
| S01 | 준비 자식 → 공개 확인 자식 → 공격 자식 1개(읽기·덮어쓰기·rename·노트·표식 삭제) |
| S02 | 준비 자식 → 공개 확인 자식 → 파일별 openssl 자식과 rename 담당 자식; 두 역할을 별도로 기록 |
| S03 | C 준비/확인 자식 → 일반 읽기 자식 → 허니팟 접근 자식 → B 준비/확인 자식 → 삭제 자식 |
| S04 | 준비 자식 → 공개 확인 자식 → 공격 자식 1개(읽기·부분 덮어쓰기·rename·노트) |

`scenarios.workers.registered_worker`와 `child_gate`의 등록 확인 → START → exec 흐름을 재사용한다.
exec 전후 PID와 시작 tick은 유지되지만 실행 파일은 바뀌므로, 등록 시 gate의 exe를 실제 공격 도구의 신뢰 판정 근거로 쓰지 않는다.
등록 요청은 관리자에서 직렬 처리한다. 자식들이 runner의 stdin 응답을 경쟁해서 읽지 않게 한다.
준비/확인 함수는 현재 `scenario_lib.run_in_child`로 미등록 fork를 생성하므로 CLI main 전체를 그대로 실행해서는 웹 계약을 충족할 수 없다.
기존 CLI 호환성을 유지하면서 작업 함수와 프로세스 생성 지점을 분리해 재사용한다. 웹 실행 중 미등록 자식이 파일 작업을 수행하지 않도록 검사한다.
프로세스는 runner 그룹을 상속하고 새 세션으로 이탈하지 않는다. 등록 거절·응답 EOF·START 통로 종료 시 작업을 시작하지 않는다.

### Huntress 허니팟 경로

원본은 target의 상위 경로에서 honeypot을 추정하고, 기존 미끼에 접근만 시도한다. 웹에서는 공통 경로 설정으로 실제 mount의 허니팟을 확인하며 임의 추정 fallback을 사용하지 않는다.
허니팟에 더미 파일을 생성하거나 기존 미끼를 삭제하지 않는다.
허니팟은 고유 workspace 밖이므로 해당 하위 작업의 허용 대상 경로를 별도로 기록한다.
이벤트 수집은 등록 PID·checkpoint·관찰 구간과 정확한 허용 경로를 함께 사용하며, mount 전체로 필터를 넓히지 않는다.
경로 없는 정책 기록은 계속 `pid_only_events`로 남긴다. 미끼 부재(ENOENT)는 차단의 근거가 아니다.

## 진행 단계와 결과 의미

화면 단계는 `PRECHECK → PREPARE → VERIFY_READY → ACTION → PROCESS_CLEANUP → COLLECT_EVENTS`를 기준으로 한다.
ACTION에는 시나리오별 하위 작업을 표시한다. 프로세스 정리와 이벤트 수집은 runner가 담당하며 관리자 작업 성공 이벤트로 대신 표시하지 않는다.
준비 실패 시 ACTION은 시작하지 않는다. 중단·오류 이후 실행하지 못한 단계는 기존 `skipped`로 표시하고 '검증하지 못함'으로 설명한다.

각 작업은 예정/시도/완료 수, 경로, 작업 PID, 오류 errno, 실패 연산을 기록한다.
원본의 `[SIM]` 일반 출력은 진단용 stderr로 보내고 stdout은 최종 JSON 하나로 유지한다.

| 상황 | 실행 결과 처리 제안 | 탐지·보호 해석 |
| --- | --- | --- |
| 모든 예정 작업 완료, 정상 종료 및 그룹 정리 확인 | 기존 `passed` | 모의 파일 작업 완료만 의미; `not_checked` 유지 |
| 파일 연산 실패 | 기존 `failed`, 완료 수와 실패 연산/errno 보존 | '파일 작업 실패'; 정책 차단 여부는 관련 로그로 별도 관찰 |
| EACCES/EPERM 또는 SIGSTOP 관찰 | 실패/시간 초과 사실과 관찰 근거를 각각 기록 | 오류/정지 단독으로 정책 차단 확정하지 않음 |
| 작업 제한 또는 runner 전체 제한 도달 | `timed_out`으로 연결; 부분 완료 수 보존 | 시간 초과를 탐지 성공으로 해석하지 않음 |
| 사용자 중단 후 그룹 종료 확인 | 기존 `cancelled` | 후속 지연 COMMIT 가능성 명시 |
| 프로세스 정리 확인 실패 | 기존 실패·새 실행 차단 유지 | 종료 완료로 표시하지 않음 |
| 이벤트 누락/읽기 실패 | `event_collection.issues` 기록 | 파일 작업 결과와 별개; 보호 여부 판정 불가 |

Huntress 허니팟 단계는 5개 경로의 접근 결과를 기록하는 관찰 작업이다. 모든 시도가 기록되면 관찰 작업 자체는 완료할 수 있으나 읽기 성공/거절/부재를 별도 집계한다.
그 외 작업은 파일 개수뿐 아니라 rename·노트·표식 삭제 등 예정 연산까지 완료되어야 작업 완료로 본다.
현재 CLI는 duration으로 루프를 빠져나가거나 표식 삭제가 실패해도 종료 코드 0일 수 있고, 허니팟 접근도 오류를 기록한 뒤 0을 반환한다.
따라서 CLI 종료 코드만 웹의 passed에 연결하지 않는다. 로컬 작업 제한의 `timed_out` 전달과 상세 결과 형식은 공통 실행 구조 커밋에서 구현한다.
underlay 변경 관찰은 시점이 있는 스냅샷으로 기록한다. 헤더 일부가 같다는 사실을 전체 파일 보존으로 세지 않으며, 해시 비교 불가 파일은 미확인으로 남긴다.

## 커밋 순서와 검증

### 다음 코드 작업의 파일별 순서

현재 단계에서는 아래 코드 작업을 수행하지 않았다. README와 계획 문서만 갱신했다.

1. **테스트 진입점 정비**: backend 테스트가 실제 활성 catalog의 기존 S01에 의존하는 부분을 조사하고, 실행 제어 테스트는 명시적인 테스트용 Scenario 정의로 분리한다. 기존 정상 작업의 직접 실행 테스트와 등록·그룹 정리 검사는 유지한다. ID를 일괄 치환하지 않는다.
2. **`scenarios/catalog.py`**: 새 S01~S04 설명과 단계 정의로 교체하고 기존 S05 항목을 제거한다. 초기에는 네 항목 모두 비활성화하고 미연동 사유를 표시한다. 기존 정상 작업을 새 S01로 실행하지 않게 한다.
3. **`demo-web/backend/app/schemas/run.py`**: 요청 ID 범위를 S01~S04와 맞춘다. 알 수 없는 ID와 미연동 ID 요청의 응답을 확인한다.
4. **`demo-web/backend/app/services/runner.py`**: 모듈 단일 문자열 검사, `s01_` 고정 workspace, S01 전용 인자 구성을 명시적인 실행 정의로 일반화한다. 지원 모듈과 CLI 인자 계약을 함께 검증하며 catalog에 module 문자열이 있다는 이유만으로 실행하지 않는다. 미구현 모듈을 허용 목록에 미리 추가하지 않는다.
5. **공통 결과 계약**: 부분 완료 수와 작업 제한 결과를 전달하는 형식을 정하고 `_validate_result`, 단계 매핑, 최종 상태 처리를 함께 수정한다. stdout 최종 JSON, stderr 진행 보고, 직렬 PID 등록, START 대기 계약을 유지한다.
6. **회귀 검사**: catalog 목록/비활성 항목 거절, 허용하지 않은 모듈 거절, 시나리오별 workspace·인자 전달, 기존 등록/중단/그룹 정리 검사를 수행한다. 공통 구조 단계에서는 실제 공격 모의 실행을 요구하지 않는다.
7. **다음 개별 연동 커밋**: `scenarios/s01_icefire.py`와 필요한 재사용 함수 분리를 구현한다. 검증 후 S01만 활성화한다. 같은 방식으로 S02~S04를 이어간다.

`PROCESS_CLEANUP`과 `COLLECT_EVENTS`를 catalog의 시나리오 작업 단계에 무조건 넣지 않는다. 현재 단계 완료 판정은 시나리오가 보고하는 작업명에 연결되므로 runner 후처리 표시와 함께 설계해야 한다.
프런트는 목록 API를 사용하지만 기본 선택 S01·세션 복원·결과 표시가 새 구성에서도 맞는지 확인한다.
전환 전 실행 중인 테스트는 먼저 종료·정리를 확인하고, API/웹을 재시작해 기존 S01 실행 기록이 새 IceFire 설명과 섞이지 않게 한다.

### 유지 및 제거 범위

- 유지: `common.py`, `workers.py`, `child_gate.py`, `__init__.py`, 기존 정상 작업과 모든 유효한 테스트, experiments 원본 및 CLI.
- 제거 예정: catalog의 사용하지 않는 기존 S05 항목과 새 구성에 맞지 않는 설명. 이번 문서 단계에서는 코드 삭제 없음.
- 현재 삭제할 Python 파일은 없다. 네 새 파일은 내용 구현 없이 미리 만들지 않는다.
- `docs/demo-web-progress.md`는 로컬 대화 재개용 기록으로 별도 관리하며 커밋 대상에서 제외한다.

### 전체 작업 단위

1. **시나리오 구성 및 연동 계획 문서화**: 본 문서와 진행 기록 갱신. 런타임 변경 없음.
2. **공통 실행 구조 준비**: 명시적인 허용 목록과 실행 연결부 마련. 기존 정상 작업 및 실행 제어 회귀 검사.
3. **S01 IceFire 연동**: 고유 workspace, PID 등록, 시작 대기, 진행·결과·이벤트 연결. Ubuntu 정상 종료·중단·재실행 확인 후 활성화.
4. **S02 DarkRadiation 연동**: openssl 자식의 등록·시작·종료 정리 검증 후 활성화.
5. **S03 Huntress 연동**: 작업 구성 확정 후 각 작업의 PID·경로·이벤트 범위 검증 후 활성화.
6. **S04 Akira 연동**: 부분 덮어쓰기 옵션과 실행·중단·결과 검증 후 활성화.
7. **웹 시연 화면 및 통합 검증**: 설명·관찰 한계 표시 통일. 연속 실행·새로고침 복원·실패 복구 및 시연 절차 기록.

각 코드 작업은 기존 의존성으로 가능한 로컬 검사를 수행하고, 실제 Ubuntu mount 검증과 구분해 기록한다.
실제 실행에서는 정상 종료, 중간 중단, 정지된 작업 정리, 다른 실행/PID 혼입 방지, 다음 실행 가능 여부를 확인한다.
검증이 끝난 최소 단위마다 사용자에게 커밋 시점을 알린다. 스테이징과 커밋은 사용자가 직접 한다.
